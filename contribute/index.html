If you want to help

Azimuth is built by one photographer, in the open, against his own archive. It is looking for photographers who own theirs. You do not need to read the architecture to contribute — the project runs on a small set of files a stranger can read, and each of them is a way in.

Bring a library

Point it at a folder of your own photographs and cull one shoot with the keyboard. Every surface is developed against one real 150,000-photo archive; a second real archive finds what one cannot — a camera it has not met, a folder layout it did not expect, a drive that goes away. Nothing you point it at is uploaded anywhere, and it never moves, renames or deletes an original.

git clone https://github.com/Sean-Kenneth-Doherty/azimuth-photo.git
cd azimuth-photo
python -m venv web\.venv
web\.venv\Scripts\python.exe -m pip install -r web\requirements-v2.txt
npm ci
.\scripts\start_azimuth_windows.ps1

It asks where it should live, then for a folder of photographs, and the library fills while you watch. INSTALL.md covers the frozen build.

File a finding, not a bug

docs/FINDINGS.md is the ledger every audit writes into, and a row closes only in the commit that does the work — 555 rows since 9 September, and this is how they got fixed. A finding has four fields:

User impactWhat it did to you, in product words. “The window opened after twenty seconds of reindexing.” Not “P3 is slow.”
EvidenceWhere: the file and line, checked at the current main. A screenshot is evidence too.
The fixThe concrete change, as specifically as you can say it. “Run the repairs behind the first paint” is a fix; “make it faster” is a wish.
How much it mattersIts rank within its surface. Be honest — a ledger where everything is urgent has no information in it.

Open an issue with those four things and it becomes a row. If you can, say what surface it belongs to (grid, loupe, rank, sidebar, search, people, import) so it lands in the right round.

Add a journey

scripts/journeys/ holds one small script per thing a photographer actually does — cull by keyboard, look closer, introduce someone, find a frame from memory, judge a burst, make an album. Each runs through the off-screen rig to a screenshot, and the gallery is read side by side with the last round's. If a real task you do is not covered, a ten-line journey for it is a contribution, and it will be run on every round after.

What is open

  • Develop. The crop and the metadata round-trip ship. The slider workspace is parked on a measured tone-parity gap — 0.0445 ΔL against a 0.035 bar — with the owner's Lightroom screenshots as the spec. The colour mathematics lives in web/pixels/ as pure functions over arrays; closing that gap is real, hard, and well-defined.
  • The taste program. Experiments E1 and E3–E5 in docs/taste-and-culling-research.md are written and not yet run. The head is linear and stays linear; the facets are stored facts. Someone who likes fitting small models on real judgements would enjoy this.
  • A phone. Deleted with V1, to return as new work against the V2 vocabulary once the desktop is finished. The bridge is one object with typed verbs; a client is a second surface on it.
  • Sharing. Four overlapping V1 systems for handing someone a photograph were deleted. There is no design yet, which is the interesting part.
  • Other platforms. The app is one Python process and one bundled document; today the native shell is proven on Windows only.

How the work runs

The loop is written down in the Field Log: the asks in MASTER_PLAN.md verbatim, the findings in the ledger, a second model refuting every diff, gates that count couplings, journeys that prove behaviour, and nothing done until it ran. Pull requests are read the same way — the diff is refuted before it is praised, and a change that deletes what it replaces is the shape that gets in. The code is AGPL-3.0.
